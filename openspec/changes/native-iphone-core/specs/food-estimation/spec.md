# 食物估算规格

## Purpose

个人版在 iPhone 本机管理任务，用户授权后直接调用千问 HTTPS 接口识别饮食。记录、照片、人工热量和 iCloud 备份不依赖识别服务；既有私有服务仅作为可选适配器保留。

## ADDED Requirements

### Requirement: 直接调用前明确授权
应用 MUST 在首次发送前展示千问供应商、模型、发送的照片与备注、供应商处理与保留说明、费用由用户自己的模型账户承担，并取得明确授权。自动估算开关不得代替授权；模型、端点或已展示政策变化 SHALL 要求重新确认。撤回授权 MUST 阻止全部新发送并取消本机待处理任务；已经送达供应商的资料不能保证追回。

#### Scenario: 未授权时添加照片
- **WHEN** 用户保存带照片的饮食但尚未授权千问
- **THEN** 原始饮食正常保存在本机，不发出图片或备注请求，热量仍可人工填写

#### Scenario: 更换千问 API Host
- **WHEN** App 更新预置的千问调用地址
- **THEN** 旧地址的密钥和授权不得自动用于新地址；用户在手机配置新密钥并重新确认发送范围前，不发送照片或备注

### Requirement: 密钥只留在本机
应用 MUST 让用户在手机上输入自己的千问 API Key，存入不可同步的本机 Keychain；密钥不得进入 App 包、导出、备份、日志、任务持久化或普通界面。正式请求 MUST 只发往预置的千问 HTTPS 端点，不接受由饮食内容或远端响应提供的目的地或重定向。

#### Scenario: 导出资料
- **WHEN** 用户在配置千问后导出或备份资料
- **THEN** 包中没有 API Key 或可直接复用的授权；另一设备导入后仍需自行配置和授权

### Requirement: 无配置不产生伪造估算
应用 SHALL 区分未配置、未授权、待联网、识别中、成功、失败、取消及结果未知。只有真实千问响应经过结构和数值校验后才可成为模型估算；没有密钥、未授权、离线或识别失败时原始记录仍可保存，热量保持未知或人工值。

#### Scenario: 没有模型密钥
- **WHEN** 用户对真实餐食点击识别而未配置千问
- **THEN** 应用提示先配置或手动填写，不返回样例热量

### Requirement: 自动和手动识别遵循同一版本规则
在已授权且开启自动估算时，成功保存且含照片的新输入版本 SHALL 排队一次；用户也可对有照片或备注的当前版本手动识别。离线任务 MUST 持久化；重新联网时核对资料集、记录、输入版本、删除状态和授权。重复触发同一活动任务不得产生第二次调用。

#### Scenario: 离线修改多次
- **WHEN** 用户离线连续修改同一餐照片或备注后恢复联网
- **THEN** 仅当前有效输入版本可发送，旧排队版本失效

### Requirement: 直连调用有明确费用和重试边界
应用 SHALL 在本机保存每日尝试计数并设置可见的默认上限；供应商账户预算仍由用户自行设置。网络请求一旦可能已送达供应商，超时、进程终止或响应丢失 MUST 成为结果未知，不得自动重发；用户明确重试时须提示可能重复计费。请求发送前的可确定离线错误可以等待联网重试。提供的私有服务适配器可以继续保持其服务端幂等语义，但不是个人版的必备部署条件。

#### Scenario: 请求结果未知
- **WHEN** 已发出的千问请求在返回前失去响应
- **THEN** 本机保留餐食并显示结果未知，不自动调用第二次；用户可明确重试或人工填写

### Requirement: 模型输出必须校验
应用 MUST 将照片及备注中的指令当作不可信素材，仅接受一条可解析为 JSON 的文本模型回复，校验食物项、份量、热量、假设、合计、来源和真实模型标识。非有限数值、负值、项目合计不一致、无有效项目、范围不包围合计或整餐超过 10000 kcal MUST 被拒绝；无法识别时不得补造零值。千问官方将 qwen3-omni-flash 列为不支持结构化输出的旧型号，客户端 SHALL 仅提示 JSON 并自行严格校验，不发送不兼容的 `response_format`，也不通过第二次模型调用自动修复。

#### Scenario: 模型合计错误
- **WHEN** 两项各 200 kcal 但模型合计写为 900 kcal
- **THEN** 结果不能计入当前摄入，原始记录和人工录入仍可用

### Requirement: 迟到结果不能覆盖新事实
应用 MUST 只有在记录仍存在且未删除、任务输入版本与记录一致、授权仍有效且任务之后未发生人工修正时采用结果。其他结果 SHALL 被丢弃或只留作不计入统计的历史。

#### Scenario: 结果返回前人工填热量
- **WHEN** 用户手动确认 600 kcal 后旧模型结果返回 500 kcal
- **THEN** 当前热量保持 600 kcal，旧结果不得静默覆盖

### Requirement: 人工修正保留来源和历史
应用 SHALL 支持手动填写整餐热量及逐项名称、克数、热量，支持添加和移除食物项。修改已知且大于零的克数 SHALL 按比例调整热量，直接填写热量以用户值为准；保存 MUST 校验有限非负值、非空名称和整餐上限，并保留原始模型估算与历次人工修正。

#### Scenario: 按比例调整份量
- **WHEN** 用户把 100 g、200 kcal 改为 150 g
- **THEN** 该项变为 300 kcal，整餐合计同步更新，确认后来源为人工修正
